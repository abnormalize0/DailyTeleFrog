# 0037. Настроить пул соединений SQLAlchemy и убрать гонку инициализации Engine

## Проблема
Пул соединений SQLAlchemy создаётся лениво при первом запросе без проверки «живости» и пересоздания простаивающих соединений, что приводит к падениям после простоя БД и к гонке при старте.

## Как возникает и к чему приводит
- *Как возникает:* в `src/api/shared.py::get_session()` глобальный `_engine` инициализируется лениво (`if _engine is None: _engine = create_engine(db_url, isolation_level="READ COMMITTED")`) без `pool_pre_ping=True` и `pool_recycle`.
- *Негативный эффект:*
  - MySQL закрывает простаивающие соединения по `wait_timeout` (по умолчанию 8 часов), после чего SQLAlchemy берёт из пула мёртвый сокет и запрос падает с 500 (`MySQL server has gone away`);
  - при одновременных первых запросах в многопоточном режиме два потока могут оба пройти проверку `_engine is None` и создать два пула соединений, потеряв ссылку на первый;
  - отсутствие или некорректность `MVP_DB_URL_*` обнаруживается не при старте приложения, а только на первом HTTP-запросе.

## Желаемое поведение
- Перенести создание `Engine` в явную функцию `init_db(url: str)` и вызывать её при старте приложения (в WSGI-фабрике / `run_server`), чтобы ошибка конфигурации БД ловилась сразу на старте (fail-fast), а `get_session()` не имела гонки.
- Передать в `create_engine(...)` параметры `pool_pre_ping=True` и `pool_recycle=3600` (при сохранении `isolation_level="READ COMMITTED"`).
- Оставить в коде комментарий о недопустимости `gunicorn --preload` без `post_fork` (`engine.dispose()`), чтобы пул соединений не делился между форкнутыми воркерами.

## Готово, когда
- `Engine` инициализируется явно на старте через `init_db(url)` и не создаётся лениво в `get_session()`.
- В `create_engine` заданы `pool_pre_ping=True` и `pool_recycle=3600`.
- Есть unit-проверки инициализации и параметров `Engine`.
- Прогнан `black` и полный `make test` проходит.
