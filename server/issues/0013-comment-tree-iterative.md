# 0013. Убрать рекурсию, O(N²) и недетерминированный порядок при сборке дерева комментариев

## Проблема
`GET /articles/{id}` падает с `500 RecursionError` на глубокой ветке ответов, работает за квадратичное время `O(N²)` по числу комментариев статьи и возвращает комментарии внутри одного уровня без гарантированной сортировки.

## Как возникает и к чему приводит
- *Как возникает:* в `src/db/comment.py::from_article` все комментарии статьи вычитываются одним запросом без `ORDER BY`, а затем дерево строится взаимной рекурсией `_tree_node` ↔ `answers` (~2–3 Python-фрейма на уровень вложенности). При этом функция `answers` на каждом узле заново линейно просматривает весь список комментариев статьи (`if comment.parent_id == id`). Схема `comments.parent_id` и `POST /articles/{id}/comments` никак не ограничивают глубину вложенности.
- *Негативный эффект:*
  - при глубине ветки ~330 ответов Python достигает `sys.getrecursionlimit()` (1000) и `GET /articles/{id}` начинает стабильно возвращать `500 Internal Server Error` — страница статьи становится полностью недоступной для чтения, хотя новые ответы продолжают добавляться без ошибок;
  - из-за сложности `O(N²)` статья с большим количеством комментариев резко замедляет сервер (на 10 000 комментариев — 100 млн итераций на каждый просмотр страницы);
  - без `ORDER BY` порядок комментариев на одном уровне не детерминирован и может меняться между запросами.

## Желаемое поведение
- `src/db/comment.py::from_article` строит дерево комментариев итеративно (без рекурсии) за линейное время `O(N)` — через индексирование узлов по `id` за один-два прохода.
- Выборка комментариев статьи из БД выполняется с детерминированной сортировкой (`ORDER BY creation_date ASC, id ASC` — от старых к новым), чтобы порядок комментариев на каждом уровне был стабильным и предсказуемым.
- `GET /articles/{id}` стабильно возвращает `200 OK` на глубоких ветках (в том числе глубже `sys.getrecursionlimit()`), без `RecursionError` и деградации производительности.

## Открытые вопросы
- Нужно ли дополнительно защититься от `RecursionError` в `json.dumps` (и `JSON.parse` / рекурсивного рендера на клиенте) на экстремально глубоких ветках (порядка 5000+ уровней): ввести лимит глубины ответов в `POST /articles/{id}/comments` (например, 50–100 уровней), перейти на плоский список комментариев с `parent_id` или осознанно оставить без лимита на этапе прототипа?

## Готово, когда
- `comment.from_article` работает итеративно за `O(N)` и сортирует комментарии по `creation_date ASC, id ASC`.
- Глубокая ветка комментариев (например, 500+ уровней) корректно отдаётся в `GET /articles/{id}` с кодом `200`, без `500 RecursionError`.
- Рассмотрен открытый вопрос об экстремальной глубине вложенности (принято решение: ввести лимит, поменять формат или осознанно отложить).
- Добавлены регрессионные тесты (unit на `comment.from_article` для глубокой ветки и порядка комментариев + e2e на `GET /articles/{id}`), полный `make test` проходит.
