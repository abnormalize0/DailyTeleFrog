# 0024. Перенести пагинацию ленты в SQL (LIMIT/OFFSET) и добавить вторичный ключ сортировки

## Проблема
При формировании ленты `GET /articles` из MySQL выгружаются `id` **всех** подходящих статей без `LIMIT`/`OFFSET`, а на страницы список режется уже в Python. Кроме того, в `ORDER BY` отсутствует вторичный ключ (`Article.id`), из-за чего порядок статей с одинаковым рейтингом или одинаковой датой создания не детерминирован.

## Как возникает и к чему приводит
- *Как возникает:* в `src/db/article.py::pages_get` запрос завершается `query.order_by(order_expr.desc() / .asc())` без вторичного ключа и делает `query.all()`. Затем `src/backend.py::pages_get` режет весь полученный список срезом `article_ids[start:end]`.
- *Негативный эффект:*
  - с ростом числа статей каждый запрос `GET /articles?indexes=0` вычитывает и пересылает из MySQL в Python полный список ID всех статей базы (десятки/сотни тысяч строк), чтобы взять из них 5 штук;
  - без вторичного ключа сортировки (`Article.id`) статьи с равным `rating` (например, все новые статьи с рейтингом `0`) или равным `creation_date` могут возвращаться MySQL в разном порядке между запросами разных страниц — одна статья дублируется на соседних страницах, а другая пропадает из выдачи.

## Желаемое поведение
- В `src/db/article.py::pages_get` в `ORDER BY` добавляется детерминированный вторичный ключ `Article.id` в том же направлении, что и основная сортировка:
  - `descending`: `ORDER BY order_expr DESC, Article.id DESC`;
  - `ascending`: `ORDER BY order_expr ASC, Article.id ASC`.
- Пагинация выполняется на уровне SQL через `LIMIT` и `OFFSET` — из БД выгружаются только ID статей, попадающих на запрошенные страницы `indexes`.
- Для смежных индексов (например, `[0, 1, 2]`) выполняется один SQL-запрос с общим `OFFSET`/`LIMIT`; для разреженных индексов (например, `[0, 1000]`) запросы группируются по смежным диапазонам (с учётом лимита 10 элементов из `issues/0011-articles-indexes-validation.md`), чтобы не выгружать промежуточные тысячи ID.
- Внешний контракт `GET /articles` (формат `indexes` и `pages`) остаётся полностью совместимым с клиентом.

## Готово, когда
- `article.pages_get` использует SQL `LIMIT`/`OFFSET` и не выгружает ID всех статей таблицы в Python (в том числе при разреженных `indexes`).
- В `ORDER BY` добавлен вторичный ключ `Article.id` (в направлении `sort_direction`), и порядок статей с равным `rating` или `creation_date` стабилен между страницами.
- Добавлены регрессионные unit- и e2e-тесты (проверка стабильности границ страниц при равных рейтингах/датах и проверка, что SQL содержит `LIMIT`/`OFFSET`), полный `make test` проходит.
