# 0015. Вынести подписки и блокировки в отдельные REST-эндпоинты с поддержкой снятия

## Проблема
В API нет способа отписаться от пользователя/тега или снять блокировку, вернув нейтральное состояние (можно только переключить подписку в чёрный список и обратно). При этом управление подписками и блокировками сейчас встроено в `PATCH /users/me` через единственные во всём API поля в `kebab-case` (`sub-tags`, `blocked-tags`, `sub-users`, `blocked-users`), которые к тому же расходятся по именованию с ответом `GET /users/me` (`sub_tags`, `blocked_tags`, `sub_users`, `blocked_users`).

## Как возникает и к чему приводит
- *Как возникает:* в `src/db/user.py` реализованы только `sub_user`, `block_user`, `sub_tag`, `block_tag`, которые переводят цель в один из двух списков, но нет функций удаления связи. В `src/api/routes/users_me.py` и `src/api/api_info.py` эти списки добавлены как опциональные поля `PATCH /users/me` в `kebab-case`, смешанные с полями самого профиля (`nickname`, `email`, `avatar`, `description`).
- *Негативный эффект:*
  - пользователь, один раз подписавшийся на автора/тег или заблокировавший его, вообще не может вернуть нейтральное состояние;
  - `PATCH /users/me` смешивает обновление полей профиля и управление связями, причём использует несогласованный `kebab-case`, выбивающийся из остального API (`snake_case`).

## Желаемое поведение
- Подписки и блокировки пользователей и тегов вынесены в отдельные REST-эндпоинты по единому стилю с реакциями из `decisions/0004-rest-api.md`:
  - `PUT` — идемпотентно оформляет подписку или блокировку (снимая противоположное состояние, если оно было), отвечает `204 No Content`;
  - `DELETE` — идемпотентно снимает подписку или блокировку (повторный вызов, когда связи уже нет, тоже отвечает `204 No Content`), возвращая нейтральное состояние.
- Старые поля `sub-tags`, `blocked-tags`, `sub-users`, `blocked-users` удалены из `PATCH /users/me` — `PATCH /users/me` отвечает исключительно за поля профиля (`nickname`, `email`, `avatar`, `description`), а `GET /users/me` продолжает отдавать текущие списки `sub_tags`, `blocked_tags`, `sub_users`, `blocked_users`.
- Существующие ограничения сохраняются: подписка/блокировка самого себя возвращает `403`, несуществующего или удалённого пользователя — ошибку валидации/отсутствия ресурса, пустой тег — `400`.

## Открытые вопросы
- Какие точные URL-пути использовать для подписок и блокировок пользователей и тегов и как передавать `tag_name` (в сегменте пути с ограничениями/кодированием спецсимволов вроде `/` и `?` или в query/теле запроса)?

## Готово, когда
- Перед реализацией проведён grill по контракту новых эндпоинтов, принятое решение зафиксировано в `decisions/` (и описаны изменения для клиентской части).
- Добавлены функции снятия подписок и блокировок в `src/db/user.py` и новые REST-эндпоинты (`PUT`/`DELETE`) в `src/api/routes/` + `src/api/api_info.py`.
- Поля `sub-tags`, `blocked-tags`, `sub-users`, `blocked-users` убраны из `PATCH /users/me` (`api_info.py`, `backend.py`, `routes/users_me.py`, `decisions/0007-input-rules.md`).
- Каждый новый метод покрыт unit- и e2e-тестами (включая идемпотентность, ошибки и атомарность), полный `make test` проходит.
