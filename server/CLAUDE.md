# CLAUDE.md

Этот файл содержит инструкции для Claude Code (claude.ai/code) при работе с кодом в этом репозитории.

## Запуск сервера

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r deployment/requirements.txt
```

Конфигурация читается из файла `.env` в корне `server/`: `MVP_DB_URL_TEST` / `MVP_DB_URL_PRODUCTION` (SQLAlchemy DB URL) и `MVP_PATH` (корень рабочей директории, внутри контейнеров — `/app`).

```bash
python3 start.py                                    # продакшн-режим, использует MVP_DB_URL_PRODUCTION
python3 start.py -t                                  # тестовый режим, использует MVP_DB_URL_TEST
python3 start.py -t --working-directory <dir>        # предварительно перейти в <dir> (логи пишутся в <dir>/log)
```

Схема базы данных не создается через `start.py` — она должна уже существовать (см. ниже, как её создает тестовый набор).

Docker: `make` без аргументов выводит список всех целей. Порядок сборки важен — `code_server.dockerfile` начинается с `FROM os_server:1.0`, поэтому сначала собирается `make build-os`, потом `make build-code`.

## Запуск тестов

Отдельного слоя юнит-тестов/моков нет: каждый тест в `tests/test_api.py` в `setUp` поднимает настоящий серверный процесс `start.py -t` поверх настоящей базы данных, а перед каждым тестовым методом все таблицы удаляются и создаются заново из `scheme.Base.metadata`. Тесты общаются с сервером только по HTTP через `requests`.

Запуск всего набора в docker (собирает образы, поднимает MySQL и сервер, копирует логи в `test_logs/`):

```bash
make test
```

Запуск подмножества или одного теста — флаги `run_tests.py` внутри контейнера:

```bash
docker exec -t server-test python3 /app/tests/run_tests.py -R test_login_get   # поиск по regexp в имени теста
docker exec -t server-test python3 /app/tests/run_tests.py -N                 # показать подходящие тесты без запуска
docker exec -t server-test python3 /app/tests/run_tests.py -E -R test_users    # запустить все, кроме подходящих
docker exec -t server-test python3 /app/tests/run_tests.py --repeat 5          # повторить запуск N раз
```

`-R` ищет через `re.search` по строке `module.ClassName.method_name`, поэтому достаточно голого имени метода. Для обнаружения тестов обязателен префикс `test_` и в имени файла, и в имени метода.

**Каждый API-метод должен иметь свой отдельный end-to-end тест** в `tests/test_api.py` (один `test_<метод>_<тип>` на каждый `api_<метод>_<тип>`), а не полагаться на то, что его затронет тест другого метода.

## Стиль кода

Весь Python-код оформляется по стилю `black` (без конфигурационного файла, настройки по умолчанию). Прогонять после каждой выполненной задачи:

```bash
python -m black src tests start.py
```

**Каждая функция должна иметь понятный докстринг-хелпер**: короткое описание того, что делает функция, затем секции `Args:` и `Returns:` — так, как уже оформлены функции в `src/`. Пример:

```python
def get_email(session: Session, username):
    """Возвращает email пользователя.

    Args:
        session: сессия SQLAlchemy.
        username: имя пользователя.

    Returns:
        Кортеж (`Status`, str):
            - OK и email — если пользователь найден.
            - ValueError и `None` — если пользователь не найден.
    """
```

**Каждый файл должен начинаться с описания того, зачем он нужен и какую смысловую нагрузку несет** (одно-два предложения в module docstring), например:

```python
"""
Этот файл служит для хранения логики выполнения запросов, не связанной с изменениями в базах данных.
"""
```

**Комментарии внутри кода объясняют «почему», а не «как».** Если строка кода и так понятна по названиям переменных/функций — комментарий не нужен. Комментарий уместен, когда есть неочевидное ограничение, побочный эффект или причина, по которой сделано именно так (а не иначе), а не когда он просто пересказывает следующую строку кода.

## Простота изменений

Любые правки должны быть максимально простыми и minimal-diff: решать именно поставленную задачу, не заниматься попутным рефакторингом и не добавлять код "про запас". **Нельзя вводить новую зависимость от библиотеки без явного обоснования** — сначала проверить, нельзя ли решить задачу тем, что уже есть в проекте или в стандартной библиотеке.
