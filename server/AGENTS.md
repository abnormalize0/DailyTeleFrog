# AGENTS.md

Этот файл содержит постоянные инструкции для агента при работе с кодом `server/` в этом репозитории.

## Обязательный цикл разработки

Эти правила действуют автоматически во всех задачах без напоминаний со стороны пользователя:

1. **Отдельная ветка на каждую задачу:**
   - Перед началом работы над каждой задачей из `issues/` создавай от `main` отдельную ветку с именем `issue-<номер>-<короткое-имя>` (по имени файла задачи без `.md`, например `issue-0034-sync-docs-decisions-and-skills`), если она ещё не создана. Коммиты, PR и мержи делает сам пользователь.

2. **Закрытие открытых вопросов до начала работы над задачей:**
   - Если в файле задачи (`issues/`) есть секция `## Открытые вопросы` (или любые незакрытые вопросы), ты не должен начинать решение задачи, пока не получишь от пользователя полный и однозначный ответ на каждый вопрос.
   - Если ответ пользователя неточный, неполный или допускает разные трактовки, не делай предположений сам — задавай уточняющие вопросы до полного снятия неоднозначности.

3. **Исправление любого бага — сначала падающий тест (TDD):**
   - Прежде чем менять производственный код в `src/`, сначала напиши регрессионный тест (unit и/или e2e), который воспроизводит баг. Для гонок и дедлоков тест обязан быть детерминированным (триггер `BEFORE INSERT/UPDATE ... DO SLEEP(...)` в e2e или `open_snapshot`/`commit_rows` в unit).
   - Запусти тест и убедись, что он **падает** именно из-за бага.
   - Только после этого исправляй код, убедись, что тест стал зелёным, и прогони полный `make test`.

4. **Добавление новой фичи — сначала grill, потом план работы:**
   - Не начинай писать код новой фичи сразу.
   - Сначала проведи короткий **grill** (интерактивный разбор требований и развилок): задай пользователю уточняющие вопросы (через `ask_question` или структурированный список) по контракту API, крайним случаям, ошибкам, схеме БД, правам доступа и спорным сценариям.
   - После ответов составь **короткий пошаговый план работы** (затрагиваемые файлы, схема/API, принятые решения, тесты) и дождись подтверждения пользователя.
   - Только после подтверждения плана переходи к реализации.

5. **Обязательная проверка независимым субагентом-критиком перед завершением задачи:**
   - После реализации, форматирования (`black`) и прогона полного `make test` выполни скилл `dailytelefrog-self-review` — включая обязательный запуск **отдельного read-only субагента-критика** с чистым контекстом на свой `git diff`.
   - Исправь обоснованные замечания критика и заново прогони `black` и `make test`.

6. **Итоговая сводка и название чата после завершения и пуша задачи:**
   - После завершения задачи и пуша изменений в `main` (или по просьбе пользователя подвести итог) выполни скилл `dailytelefrog-task-summary`: выведи название для сохранения вкладки чата в формате `#<номер> <краткое описание>` и краткую сводку по проделанной работе.

Для мелких однозначных правок (документация, опечатка, форматирование, точечный рефакторинг по прямой инструкции) grill и план не нужны — сразу вноси правки.

## Стек технологий

Flask (REST API, см. `decisions/0004-rest-api.md`), SQLAlchemy + MySQL (хранение данных), **pytest** (тестовый фреймворк, см. «Запуск тестов» ниже), `black` (форматирование, см. «Стиль кода» ниже).

## Запуск сервера

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r deployment/requirements.txt
```

Конфигурация читается из файла `.env` в корне `server/`: `MVP_DB_URL_TEST` / `MVP_DB_URL_PRODUCTION` (SQLAlchemy DB URL) и `MVP_PATH` (корень рабочей директории, внутри контейнеров — `/app`).

```bash
python3 start.py                                    # продакшн-режим, использует MVP_DB_URL_PRODUCTION
python3 start.py -t                                  # тестовый режим, использует MVP_DB_URL_TEST
python3 start.py -t --working-directory <dir>        # предварительно перейти в <dir> (логи пишутся в <dir>/log)
```

Схема базы данных не создается через `start.py` — она должна уже существовать (см. ниже, как её создает тестовый набор).

Docker: `make` без аргументов выводит список всех целей. Порядок сборки важен — `code_server.dockerfile` начинается с `FROM os_server:1.0`, поэтому сначала собирается `make build-os`, потом `make build-code`.

## Запуск тестов

Тесты написаны на **pytest** (обычные функции/классы с `assert`, без `unittest.TestCase`). Слоёв два, моков нет ни в одном (см. `decisions/0010-unit-tests.md`):

- **Unit-тесты** лежат в папке `tests/` рядом с проверяемым модулем (`src/db/user.py` → `src/db/tests/test_user.py`) и вызывают функции напрямую, без сервера и HTTP. Тесты, которым нужна БД, работают с настоящей MySQL: fixture `session` из `src/conftest.py` откатывает изменения после каждого теста. Остальным тестам БД не нужна.
- **End-to-end тесты** лежат в `tests/routes/`. Перед каждым тестом fixture `server` из `tests/conftest.py` удаляет и заново создаёт все таблицы из `scheme.Base.metadata`, поднимает настоящий серверный процесс `start.py -t` поверх настоящей базы данных, а после теста останавливает его. Тесты общаются с сервером только по HTTP через `requests`.

Запуск в docker (собирает образы и поднимает MySQL):

```bash
make test        # оба слоя, логи сервера копируются в test_logs/ даже при падении тестов
make test-unit   # только unit-тесты
```

Запуск подмножества или одного теста — обычные флаги pytest внутри контейнера:

```bash
docker exec -w /app -t server-test python3 -m pytest src -v                             # все unit-тесты
docker exec -w /app -t server-test python3 -m pytest tests -v                           # все e2e-тесты
docker exec -w /app -t server-test python3 -m pytest tests -v -k test_auth_login_post   # один тест (подстрока имени)
docker exec -w /app -t server-test python3 -m pytest tests --collect-only -q            # показать тесты без запуска
docker exec -w /app -t server-test python3 -m pytest tests -v -k "not test_users"       # запустить все, кроме подходящих
docker cp ./src/. server-test:/app/src/                                                 # обновить код в уже запущенном контейнере
```

`src` и `tests` запускаются раздельными командами: e2e-fixtures с `autouse` живут в `tests/conftest.py` и не должны срабатывать на unit-тестах.

Для обнаружения тестов обязателен префикс `test_` и в имени файла, и в имени метода (стандартное поведение pytest, дополнительно не настраивается). Имена файлов не должны повторяться: в проекте нет `__init__.py` в тестовых папках, и pytest не сможет собрать два `test_<имя>.py` разом.

**Оба слоя проверяют не только успешные сценарии, но и ошибки.** На каждую ошибку из докстринга функции или метода нужна проверка, и она сверяет текст целиком: `assert_error(answer, "not-found", "Cannot find article with id: 1")` в e2e-тестах и `assert_error_status(status, ErrorType.NotFound, "...")` из `src/tests/helpers.py` в unit-тестах. Клиент показывает этот текст человеку, поэтому он должен объяснять, что пошло не так. Клиентская ошибка в запросе никогда не должна превращаться в 500.

**API-метод атомарен:** при ответе 2xx применены все его изменения, при любом другом ответе не изменилась ни одна строка (см. `decisions/0009-api-atomicity.md`). Метод с несколькими записями в БД получает тест в `tests/routes/test_atomicity.py`: fixture `fail_write` вызывает настоящий сбой последней записи триггером MySQL, а `read_all_rows` читает таблицы напрямую, чтобы сравнить их до и после запроса. С сервером такой тест по-прежнему общается только по HTTP. Одновременные одинаковые запросы проверяются в `tests/routes/test_concurrency.py`: конфликт ключа не должен давать 500.

**Каждый API-метод должен иметь свой отдельный end-to-end тест** в файле своего ресурса под `tests/routes/` (один `test_<метод>_<тип>` на каждый `api_<метод>_<тип>`, в том же файле, что и `src/api/routes/<ресурс>.py`), а не полагаться на то, что его затронет тест другого метода.

## Стиль кода

Весь Python-код оформляется по стилю `black` (без конфигурационного файла, настройки по умолчанию). Прогонять после каждой выполненной задачи:

```bash
python -m black src tests start.py
```

**Каждая функция должна иметь понятный докстринг-хелпер**: короткое описание того, что делает функция, затем секции `Args:` и `Returns:` — так, как уже оформлены функции в `src/`. Пример:

```python
def get_email(session: Session, username):
    """Возвращает email пользователя.

    Args:
        session: сессия SQLAlchemy.
        username: имя пользователя.

    Returns:
        Кортеж (`Status`, str):
            - OK и email — если пользователь найден.
            - ValueError и `None` — если пользователь не найден.
    """
```

**Каждый файл должен начинаться с описания того, зачем он нужен и какую смысловую нагрузку несет** (одно-два предложения в module docstring), например:

```python
"""
Этот файл служит для хранения логики выполнения запросов, не связанной с изменениями в базах данных.
"""
```

**Комментарии внутри кода объясняют «почему», а не «как».** Если строка кода и так понятна по названиям переменных/функций — комментарий не нужен. Комментарий уместен, когда есть неочевидное ограничение, побочный эффект или причина, по которой сделано именно так (а не иначе), а не когда он просто пересказывает следующую строку кода.

**Комментарии описывают текущее состояние кода, а не историю его правок.** Никаких «было X», «раньше», «расширено при ревизии», «перенесено из»: историю хранит git, а причины решений — `decisions/`.

## Простота изменений

Любые правки должны быть максимально простыми и minimal-diff: решать именно поставленную задачу, не заниматься попутным рефакторингом и не добавлять код "про запас". При этом minimal-diff не означает локальную заплатку в обход источника правды: если корень проблемы в контракте транзакции, точке входа (например, проверке токена) или правилах БД (`src/db/scheme/base.py`), исправлять нужно на нужном слое, а не маскировать симптом. **Нельзя вводить новую зависимость от библиотеки без явного обоснования** — сначала проверить, нельзя ли решить задачу тем, что уже есть в проекте или в стандартной библиотеке.
