# Журнал решений DailyTeleFrog (ADR для агентов)

Решения уровня архитектуры записываются в `server/decisions/`, один файл на решение. Журнал решает три задачи:
1. Пользователь и агенты в любой сессии понимают, почему проект устроен именно так, и не перерешают одно и то же заново.
2. Агенты автоматически находят и соблюдают правила, которые следуют из решений.
3. Решения часто принимаются в рамках одной задачи, а реализуются позже, поэтому журнал заодно служит списком отложенной работы.

Комментарии в коде объясняют конкретное место. Журнал хранит решения, которые затрагивают несколько файлов, клиент или будущие задачи. Общие правила проекта (только `server/`, текст на русском, идентификаторы на английском, коммиты делает пользователь) берутся из скила `dailytelefrog-backend`.

## Статусы

У записи два независимых статуса: судьба самого решения и степень его реализации. Значения в шапке пишутся по-английски, чтобы их было легко искать поиском.

`status`: судьба решения.
- `discussing`: вопрос открыт, варианты ещё обсуждаются. Агент не выбирает вариант сам: если задача упирается в этот вопрос, он спрашивает пользователя.
- `proposed`: решение предложил агент, пользователь ещё не согласился.
- `accepted`: пользователь согласился. Только такие решения обязательны для агентов.
- `superseded`: заменено другим решением (номер в поле `superseded_by`).
- `rejected`: обсудили и отказались. Запись сохраняется, чтобы не предлагать то же снова.

`implementation`: сделано или нет.
- `not-started`: в коде ещё ничего нет.
- `partial`: часть сделана, остаток в чек-листе «Что осталось сделать».
- `done`: реализовано полностью.
- `n/a`: реализовывать нечего (например, решение «пока не делаем X» или отклонённое решение).

Решение принимает пользователь. Агент сам может поставить только `discussing` или `proposed`. Статус `accepted` или `rejected` ставится после явного ответа пользователя.

## Как агенту пользоваться журналом

Перед любой задачей в `server/`:

1. Собери шапки всех записей одной командой, не открывая файлы целиком:
   ```bash
   grep -H -E '^(title|status|implementation|areas|files):' server/decisions/*.md
   ```
   Если папки нет, журнал пуст.
2. Выбери записи, у которых `areas` или `files` пересекаются с задачей.
3. Для `accepted` прочитай раздел «Правило для агента» и соблюдай его. Остальные разделы читай, если правило неоднозначно ложится на задачу.
4. Для `discussing` и `proposed` не считай решение принятым. Если задача от него зависит, скажи об этом пользователю.

Во время и после задачи:
- Если задача противоречит `accepted`-решению, не обходи его молча. Назови решение и спроси, пересматриваем ли мы его.
- Если задача реализует пункт из «Что осталось сделать», отметь пункт и обнови `implementation`.
- Если ты работаешь рядом с незавершённым пунктом из чек-листа другого решения, упомяни его в «Замечено по пути», но не делай без спроса.
- Если сработало одно из «Условий пересмотра», напомни пользователю о решении.
- В коде, который реализует решение, оставь комментарий со ссылкой, например `# См. server/decisions/0001-api-half-rest.md`.

## Когда заводить запись

Заводи запись, если выполняется хотя бы одно условие:
- было несколько разумных вариантов, и выбран (или обсуждается) один;
- решение влияет на несколько файлов, на клиент или на будущие задачи;
- сознательно отложено что-то важное («миграции потом», «пароли пока без хеша»);
- вводится новая библиотека (сюда же идёт обоснование, почему не стандартная библиотека Python).

Не заводи запись для мелочей, которые целиком объясняются комментарием в одном месте кода.

Обсуждение может идти в рамках совсем другой задачи. Если в разговоре сложилось решение или открылся важный вопрос, предложи записать его, даже если реализация будет потом (`implementation: not-started`).

## Формат записи

Имя файла: `NNNN-short-name.md`. `NNNN` — следующий номер с ведущими нулями (`0001`, `0002`, …), имя по-английски через дефис. Номера не переиспользуются. Отдельный файл-оглавление не нужен: его заменяет `grep` по шапкам, и не придётся поддерживать его в актуальном состоянии.

Значения `areas` берутся из списка: `api`, `db`, `auth`, `articles`, `editor`, `comments`, `users`, `subscriptions`, `donations`, `logging`, `tests`, `deploy`. Новую область можно добавить, если ни одна из этих не подходит. В `files` указываются пути от корня репозитория (можно с `*`).

Шаблон. Текст пишется на русском, коротко и по делу. Разделы, которым нечего сказать, можно выкинуть (кроме шапки, «Решения» и «Правила для агента»).

```markdown
---
id: 0001
title: Короткое название решения на русском
status: discussing | proposed | accepted | superseded | rejected
implementation: not-started | partial | done | n/a
areas: [api, db]
files: [server/src/api/shared.py, server/tests/routes/]
date: ГГГГ-ММ-ДД          # когда запись создана
updated: ГГГГ-ММ-ДД       # когда менялись status или implementation
superseded_by:            # номер нового решения, если status: superseded
supersedes:               # номер старого решения, если это замена
---

# 0001. Название решения

## Правило для агента
Одна-три строки в повелительном наклонении, которые можно применить, не читая остальное.
Пример: «В новых GET-методах принимай параметры только из query-строки.
Отдавай HTTP-код 400/404/500 вместе с `status` в теле.»

## Контекст
Какую проблему решаем, что было до этого, в рамках какой задачи или обсуждения возник вопрос.

## Решение
Что именно делаем. Конкретно, с именами файлов, методов и полей.
Для `discussing`: вопрос, на который нужно ответить.

## Почему
Смысл решения: какую цель оно достигает и какой довод оказался решающим.

## Варианты
По каждому рассмотренному варианту, включая выбранный:

### Вариант A (выбран)
- Плюсы: …
- Минусы: …

### Вариант B
- Плюсы: …
- Минусы: …
- Почему не выбран: …

## Примеры
Как выглядит код, запрос или ответ по этому решению. Если полезно, покажи «было / стало».
Примеры должны быть короткими и соответствовать стилю проекта.

## Последствия
Что это меняет для нового и старого кода и что нужно учесть на стороне клиента.

## Что осталось сделать
- [ ] Конкретный шаг, по которому понятно, сделан он или нет.
- [x] Уже сделанный шаг.

## Условия пересмотра
Когда решение стоит поднять снова, например «когда появятся продакшн-данные»
или «если пользователей станет больше тысячи».
```

## Правила ведения журнала

- Запись со статусом `accepted` по сути не переписывается. Чтобы поменять решение, создай новую запись с `supersedes`, а в старой поставь `status: superseded` и `superseded_by`. История того, почему раньше думали иначе, тоже ценна.
- В любой записи можно без новой записи обновлять `implementation`, `updated`, чек-лист и `files`, а также исправлять опечатки.
- Запись `discussing` можно дополнять новыми вариантами и доводами по мере обсуждения, а когда пользователь решит, перевести в `accepted` или `rejected`.
- Если запись выходит длиннее примерно двух экранов, скорее всего, в ней несколько решений, и её стоит разделить.
- Агент создаёт и правит файлы журнала только в рабочей копии и не коммитит их. В ответе он перечисляет, какие записи добавил или изменил и какие статусы поменял.
