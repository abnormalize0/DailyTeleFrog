# Работа над бэкендом DailyTeleFrog

DailyTeleFrog: хобби- и портфолио-проект пользователя. Это русскоязычная платформа статей для геймеров, помесь форума и Twitch. Центральная фича: студия автора с блочным редактором. Горизонт примерно год работы до демонстрируемого прототипа. Пользователь отвечает за бэкенд (`server/`: Flask + SQLAlchemy + MySQL); клиент (`client/`: Vue + Vuetify) ведётся отдельно, за пределами этого скила.

Сначала прочитай `server/CLAUDE.md`. Там описаны запуск, тесты и базовый стиль (black, докстринги с `Args:`/`Returns:`, описание в начале файла, minimal-diff, e2e-тест на каждый API-метод). В шапке `server/src/api/api.py` лежат правила добавления API-методов. Этот скил их дополняет. Если что-то противоречит, спроси пользователя.

## Границы

- **Работаем только в `server/`.** Клиент (`client/`, любой GUI) трогать категорически запрещено: ни правок, ни «мелких исправлений», ни форматирования. Если задача требует изменений на клиенте, опиши, что там нужно поменять, и остановись.
- Коммиты, PR и мержи делает сам пользователь. Не коммить, не пушь и не открывай PR, пока он явно об этом не попросит в текущей задаче.

## Как работаем

- **Сразу код.** План без кода не нужен, если пользователь сам его не попросил. Если попросил, покажи короткий план и жди ответа, прежде чем писать код.
- Когда у задачи есть неуказанная развилка, выбери самый простой разумный вариант и скажи, какой выбрал.
- **Техдолг упоминать, но не чинить попутно.** Если заметил проблему вне задачи (дублирование, баг, устаревший комментарий), в конце ответа допиши её отдельным пунктом «Замечено по пути». Пользователь заводит такие вещи отдельными задачами. Исключение: type hints (см. ниже).

## Язык

- Весь код и идентификаторы (переменные, функции, классы, таблицы, поля, ключи JSON, URL) на английском.
- Все комментарии, докстринги, ответы и описания задач на русском. Сообщения коммитов и описания PR тоже на русском, если пользователь попросит их подготовить.

## Простота кода

Главный принцип: код должен быть настолько простым, насколько возможно.

- Любое усложнение логики нужно обосновать. Если есть решение проще, выбирай его, даже если оно менее «красивое» или универсальное.
- **Предпочитай стандартную библиотеку Python.** Новая библиотека оправдана только тогда, когда без неё кода станет заметно больше, а в библиотеке есть понятное готовое решение. Обоснование приведи в ответе ещё до того, как добавишь зависимость в `deployment/requirements.txt`.
- Не пиши код «про запас»: никаких параметров, абстракций и настроек под гипотетическое будущее.

### Функции

- Предпочтение отдаётся коротким функциям, но функция должна иметь смысл.
- Выделяй кусок кода в функцию только если:
  1. он используется в нескольких местах, **или**
  2. функция нужна архитектуре проекта (например, слои `api` → `backend` → `db`, отдельный `api_<метод>_<тип>` на каждый запрос).
- Не выноси код в функцию «для красоты» или ради одного вызова: такое разбиение только заставляет прыгать по файлу.

### Типизация

- Type hints обязательны везде: аргументы и возвращаемые значения всех функций, включая новые API-методы.
- Если трогаешь функцию без аннотаций, можно добавить их попутно. Это единственный вид попутной правки, который разрешён без спроса.

### Обработка ошибок

- Обрабатывай ошибки везде, где их можно предвидеть: возвращай `Status` из `server/src/request_status.py` с подходящим `ErrorType` и понятным сообщением, а не бросай исключение наружу.
- В каждом API-методе должен быть главный обработчик, чтобы сервер не падал на непредусмотренных случаях. Сейчас это декоратор `@log.safe_api` из `server/src/log.py`: он логирует traceback и отдаёт 500 с `UnexpectedError`. Каждый новый метод обязан его иметь (вместе с `@log.log_request` и `@log.timer`, как у существующих).

## Формат API

API устроено по классическому REST (решение `server/decisions/0004-rest-api.md`):

- **Идентификатор ресурса передаётся в пути** (`/articles/{id}`). Параметры GET передаются в query-строке, данные POST/PUT/PATCH — в JSON-теле. Браузерный `fetch` запрещает тело у GET, поэтому GET с JSON-телом клиент вызвать не сможет.
- **Глагол выражает действие:** GET читает, POST создаёт, PUT задаёт состояние, PATCH меняет часть полей, DELETE удаляет. PUT и DELETE идемпотентны. Действия, которые не являются ресурсом, остаются POST: `/auth/login`, `/auth/refresh`, `/auth/logout`.
- **Успех:** 200 с данными, 201 с `Location` при создании, 204 без тела, если возвращать нечего. В теле только данные, служебного `status` нет.
- **Ошибка:** настоящий HTTP-код и тело в формате Problem Details (RFC 9457, `application/problem+json`) с полями `type`, `title`, `status`, `detail`, у ошибок валидации ещё `errors`. Вид ошибки задаётся `ErrorType` в `server/src/request_status.py`, новый вид добавляется в эту таблицу.

## Схема БД

- Миграций пока нет. Схема меняется «наживую» правкой моделей в `server/src/db/scheme/`, одна таблица на файл: тесты пересоздают таблицы из `scheme.Base.metadata`.
- Если изменение схемы затрагивает данные, которые отдаёт API, в ответе явно перечисли, что поменялось для клиентской части.

## Комментарии

Пользователь хочет **подробные комментарии везде**. По ним он разбирается в проекте, а Claude в следующих сессиях восстанавливает контекст принятых решений.

- Комментируй *почему*: причину решения, отвергнутую альтернативу, неочевидное ограничение, побочный эффект, связь с другими частями проекта (например, «порядок методов должен совпадать с `api_info.py` и тестами»).
- Не пересказывай строку кода словами. Вместо `# увеличиваем счётчик` пиши, зачем он нужен.
- Если принял нетривиальное решение (выбор структуры данных, формат ответа, обход ограничения MySQL/SQLAlchemy), оставь рядом комментарий, чтобы его не пришлось переоткрывать.
- Докстринги и описание в начале файла обязательны по `server/CLAUDE.md`. Они тоже должны объяснять смысл, а не только перечислять аргументы.

## Перед тем как сказать «готово»

1. Для нового или изменённого API-метода есть свой e2e-тест в `server/tests/routes/test_<ресурс>.py`, ответ на OPTIONS в `server/src/api/api_info.py`, и порядок методов совпадает во всех местах.
2. Прогнан `python -m black src tests start.py` из `server/`.
3. Тесты прогнаны (`make test`, или выборочно `docker exec -w /app -t server-test python3 -m pytest tests -v -k <имя_теста>`). Если запустить их не удалось (нет docker/MySQL), прямо так и скажи.
4. Изменения только внутри `server/`.
5. В ответе: что сделано, какие решения приняты и почему, список «Замечено по пути», если он есть.
