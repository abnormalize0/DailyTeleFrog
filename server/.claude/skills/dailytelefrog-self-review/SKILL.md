# Саморевью в DailyTeleFrog

Саморевью проверяет, что изменения соответствуют правилам проекта из скилов `dailytelefrog-backend`, `dailytelefrog-new-api-method` и `dailytelefrog-decisions`, а также из `server/CLAUDE.md`. На поиск багов в логике есть встроенный `/code-review`, его можно запускать дополнительно.

## Когда

- В конце каждой задачи, до того как сказать «готово».
- Когда пользователь просит «проверь дифф» или «сделай ревью».

## Что смотреть

Смотри весь фактический дифф, а не то, что помнишь из работы:

```bash
git status --short
git diff
git diff --cached
```

Новые неотслеживаемые файлы из `git status` прочитай целиком.

## Чек-лист

1. **Границы.** Нет изменений вне `server/`, в частности в `client/`. Дифф решает ровно поставленную задачу. Попутного рефакторинга нет, единственное исключение — type hints в затронутых функциях.
2. **Простота.** Можно ли сделать проще? У каждой новой функции несколько вызовов, или её требует архитектура. Нет кода, параметров и абстракций «про запас». Каждая новая строка в `deployment/requirements.txt` обоснована, и стандартной библиотеки для задачи не хватало.
3. **Оформление.**
   - У каждого нового файла есть module docstring о его назначении.
   - У каждой новой и изменённой функции есть актуальный докстринг с `Args:` и `Returns:`.
   - Комментарии на русском и объясняют «почему», а нетривиальные решения прокомментированы.
   - Все идентификаторы на английском.
   - У аргументов и возвращаемых значений есть type hints.
4. **Ошибки.** Предсказуемые случаи возвращают `Status` с подходящим `ErrorType` (он задаёт HTTP-код) и понятным сообщением, а не бросают исключение. На каждом API-методе стоит `@log.safe_api`. При ошибке делается `rollback`, `commit` — только при успехе, один на запрос и только в `src/api/routes/`. У метода с несколькими записями есть тест в `tests/routes/test_atomicity.py` (см. `decisions/0009-api-atomicity.md`).
5. **API.** Если дифф затрагивает API, пройдись по скилу `dailytelefrog-new-api-method`: четыре места, одинаковый порядок методов, декораторы, докстринг и отдельный тест на каждую ошибку из докстринга.
6. **Журнал решений.** Дифф не противоречит записям со `status: accepted` в `server/decisions/`. Если по ходу задачи принято новое решение, оно записано. Если реализован пункт из журнала, чек-лист и `implementation` обновлены.
7. **Базовая безопасность.** Запросы к БД идут только через ORM или с параметрами, без склейки SQL из строк. Пароли не попадают в логи и ответы. Файл `.env` и секреты не тронуты.
8. **Тесты и формат.** Прогнан `python -m black src tests start.py` из `server/`. Обязательно прогнаны оба слоя тестов, unit и e2e: `make test` запускает их вместе, и он проходит без ошибок. Выборочный прогон не заменяет полный. Новые и изменённые функции покрыты не только успешными сценариями: на каждую ошибку есть тест, который сверяет её текст целиком, и текст объясняет проблему человеку. Если запустить тесты не удалось, задача не считается готовой, и об этом нужно прямо сказать.

## Что делать с найденным

- Проблемы в своём диффе исправляй сразу, затем заново прогони black и тесты.
- Проблемы в коде, который задача не трогала (техдолг, баги, расхождения), не чини, а запиши в «Замечено по пути».

## Отчёт

В итоговом ответе по задаче коротко укажи:
- **Исправлено на ревью:** что нашлось и поправлено (или «ничего»).
- **Для клиента:** что поменялось в API и данных (или «ничего»).
- **Тесты:** результат unit- и e2e-тестов отдельно, либо почему они не запускались.
- **Замечено по пути:** список, если он есть.
