# Саморевью в DailyTeleFrog

Саморевью проверяет, что изменения соответствуют правилам проекта из скилов `dailytelefrog-backend`, `dailytelefrog-new-api-method` и `dailytelefrog-decisions`, а также из `server/CLAUDE.md`. На поиск багов в логике есть встроенный `/code-review`, его можно запускать дополнительно.

## Когда

- В конце каждой задачи, до того как сказать «готово».
- Когда пользователь просит «проверь дифф» или «сделай ревью».

## Что смотреть

Смотри весь фактический дифф, а не то, что помнишь из работы:

```bash
git status --short
git diff
git diff --cached
```

Новые неотслеживаемые файлы из `git status` прочитай целиком.

## Чек-лист

1. **Границы.** Нет изменений вне `server/`, в частности в `client/`. Дифф решает ровно поставленную задачу. Попутного рефакторинга нет, единственное исключение — type hints в затронутых функциях.
2. **Простота.** Можно ли сделать проще? У каждой новой функции несколько вызовов, или её требует архитектура. Нет кода, параметров и абстракций «про запас». Каждая новая строка в `deployment/requirements.txt` обоснована, и стандартной библиотеки для задачи не хватало.
3. **Оформление.**
   - У каждого нового файла есть module docstring о его назначении.
   - У каждой новой и изменённой функции есть актуальный докстринг с `Args:` и `Returns:`.
   - Комментарии на русском и объясняют «почему», а нетривиальные решения прокомментированы.
   - Все идентификаторы на английском.
   - У аргументов и возвращаемых значений есть type hints.
4. **Ошибки.** Предсказуемые случаи возвращают `Status` с подходящим `ErrorType` (он задаёт HTTP-код) и понятным сообщением, а не бросают исключение. На каждом API-методе стоит `@log.safe_api`. При ошибке делается `rollback`, `commit` — только при успехе, один на запрос и только в `src/api/routes/`. У метода с несколькими записями есть тест в `tests/routes/test_atomicity.py` (см. `decisions/0009-api-atomicity.md`).
5. **Логика, БД и конкурентность (попытайся сломать свой дифф).**
   - *Источник правды и старые данные:* починена первопричина на входе/в БД или поставлена заплатка на симптом? Как код поведёт себя со строками, которые уже лежали в БД до фикса (например, старые токены или записи с другим регистром)?
   - *Правила БД vs Python:* сравнение и сортировка строк, для которых действует collation MySQL (`utf8mb4_0900_ai_ci`, см. `src/db/scheme/base.py`), выполняются в SQL, а не через `==`/`casefold()`/`set` в Python? Нет ли TOCTOU-окна под `READ COMMITTED`, когда проверка и чтение/идентификация разнесены на два отдельных `SELECT` вместо одного?
   - *Блокировки всей транзакции:* если запрос меняет несколько полей или списки объектов (составной `PATCH` и т.п.), все нужные блокировки (с учётом неявных `UPDATE` и FK-блокировок `FOR SHARE`) берутся **до начала записи и в едином порядке, заданном БД**? Прогони мысленно 2+ параллельных составных запроса на предмет дедлока (MySQL 1213), а не только одиночные вызовы. Если функция `db` требует предварительной блокировки от вызывающего, это явно указано в её докстринге.
   - *Противоречивый ввод:* не зависит ли итог одного запроса от порядка ключей в JSON или порядка элементов в списке (например, одновременно подписка и блокировка одного объекта)? Если возможен конфликт — зафиксируй детерминированное правило в коде, докстринге API и тестах.
6. **API.** Если дифф затрагивает API, пройдись по скилу `dailytelefrog-new-api-method`: четыре места, одинаковый порядок методов, декораторы, докстринг и отдельный тест на каждую ошибку из докстринга.
7. **Журнал решений и отчёты.** Дифф не противоречит записям со `status: accepted` в `server/decisions/`. Если по ходу задачи принято новое решение или изменились описанные механизмы (блокировки, контракты, имена функций), соответствующая запись в `decisions/` обновлена (в том числе со статусом `proposed`). Если реализован пункт из журнала, чек-лист и `implementation` обновлены. Если в диффе есть файл аудита/ревью, в нём явно отмечено, какие пункты уже исправлены.
8. **Базовая безопасность.** Запросы к БД идут только через ORM или с параметрами, без склейки SQL из строк. Пароли не попадают в логи и ответы. Файл `.env` и секреты не тронуты.
9. **Тесты и формат.** Прогнан `python -m black src tests start.py` из `server/`. Обязательно прогнаны оба слоя тестов, unit и e2e: `make test` запускает их вместе, и он проходит без ошибок. Выборочный прогон не заменяет полный. Новые и изменённые функции покрыты не только успешными сценариями: на каждую ошибку есть тест, который сверяет её текст целиком, и текст объясняет проблему человеку. Тесты на гонки и дедлоки должны быть **детерминированными**: не полагаться на «несколько случайных раундов», а гарантированно сталкивать запросы во времени (например, через триггер `BEFORE INSERT ... DO SLEEP(...)` в e2e или `open_snapshot`/`commit_rows` в unit) и реально падать без фикса. Если запустить тесты не удалось, задача не считается готовой, и об этом нужно прямо сказать.

## Что делать с найденным

- Проблемы в своём диффе исправляй сразу, затем заново прогони black и тесты.
- Проблемы в коде, который задача не трогала (техдолг, баги, расхождения), не чини, а запиши в «Замечено по пути».

## Отчёт

В итоговом ответе по задаче коротко укажи:
- **Исправлено на ревью:** что нашлось и поправлено (или «ничего»).
- **Для клиента:** что поменялось в API и данных (или «ничего»).
- **Тесты:** результат unit- и e2e-тестов отдельно, либо почему они не запускались.
- **Замечено по пути:** список, если он есть.
