# 0001. Устройство API-методов

> Заменено записью [0004](0004-rest-api.md). Текст сохранён как история: пути, форматы и незакрытые пункты чек-листа ниже больше не актуальны.

Одна запись про всё, что касается того, как устроен и как оформляется API-метод: и структура кода вокруг него, и формат запроса/ответа. Изначально это были два отдельных файла (`0001-api-method-structure` и `0002-api-half-rest-format`) — объединены в один, чтобы всё про API-методы лежало в одном месте.

## Правило для агента

### Структура и инварианты метода
1. Код метода лежит в файле, сгруппированном по пути/ресурсу — один файл на путь (например `article.py` содержит оба метода `/article`, GET и POST), а не один общий `api.py` и не один файл на каждый `api_<метод>_<тип>`. **Реализовано** — все 17 методов разложены по `server/src/api/routes/*.py`; общие хелперы и `app` — в `server/src/api/shared.py`; `server/src/api/api.py` теперь только собирает их и запускает сервер (`run_server`).
2. У метода есть свой отдельный e2e-тест `test_<метод>_<тип>` в файле своего ресурса под `server/tests/routes/` (тот же файл, что и `server/src/api/routes/<ресурс>.py`) на каждый `api_<метод>_<тип>`. **Уже реализовано и обязательно**, не отступать.
3. У метода есть подробный докстринг (Принимает/Отдает/Ошибки/Контракт). **Уже реализовано и обязательно**, не отступать.
4. Метод атомарен: результат либо применяется целиком, либо полностью откатывается, промежуточное состояние недопустимо — через `session.rollback()`/`session.commit()` внутри `with get_session() as session:`. **Уже реализовано и обязательно**, не отступать.

### Формат запроса и ответа (половинчатый переход к REST)
5. **Параметры GET-запросов передаются в query-строке, а не в JSON-теле.** У POST (и других изменяющих запросов) данные остаются в JSON-теле. **План, не реализовано** — все методы сейчас читают параметры через `request.json` независимо от метода запроса.
6. **Ответ отдаётся с настоящим HTTP-кодом:** 200 при успехе, 400 на `OptionError`/`ValueError`, 404 если объект не найден, 500 на `UnexpectedError`. Выбор кода для спорного случая поясни комментарием. **План, не реализовано** — все методы сейчас всегда отвечают 200, включая ошибки.
7. **Тело ответа всегда содержит `status`:** `{"status": {"type": "OK"|"ERROR", ...}}`, при `ERROR` ещё `error_type` и `message`. **Уже реализовано и обязательно**, не отступать.

Пункты 2, 3, 4, 7 уже реализованы во всех 15 методах и обязательны для новых. Пункты 1, 5, 6 — план: в новых методах сразу используй их; существующие 15 методов не трогай без отдельной задачи (см. `dailytelefrog-backend`).

### Что означает «половинчатый» REST здесь
Из классического REST сюда берётся только часть, и это осознанный выбор, а не недоделка:
- **Берём:** настоящие HTTP-коды ответа (пункт 6) и стандартную семантику GET — параметры в query-строке, а не в теле (пункт 5).
- **Сознательно не берём:** ресурсно-ориентированные URL с действием через HTTP-глагол. Пути вида `/article/like`, `/article/dislike`, `/article/comment/like` остаются отдельными action-ориентированными эндпоинтами, а не одним ресурсом `/article/{id}/reactions`, управляемым методом (`PUT`/`DELETE`). Также не берём единый формат ошибки вида RFC 7807 (Problem Details) — вместо этого свой `status`/`error_type`/`message` в теле (пункт 7), который живёт параллельно с HTTP-кодом, а не вместо него.
- Из-за этого один и тот же `ErrorType.ValueError` сейчас покрывает и «поле не прошло валидацию», и «объект не найден» — при переходе на пункт 6 это нужно будет разделить хотя бы на уровне HTTP-кода (400 vs 404), не меняя `ErrorType` целиком (см. «Условия пересмотра»).

## Контекст
Решение сложилось в двух заходах в рамках одной темы — проверки всех API-методов на согласованность паттерна и последующего обсуждения формата ответа. Половинчатый переход к REST (пункты 5–7) уже был вкратце описан в скиле `dailytelefrog-backend` («Формат API», решение от 2026-09-26), но там же оговорено «в новых методах сразу используй новый формат» — то есть на практике это ещё не применено ни к одному метода. Проверка всех 15 методов подтвердила: `check_structure(request.json, ...)` используется одинаково для GET и POST, а `error_response`/`status_response` в `src/api/api.py` возвращают голую JSON-строку без кода. Эта запись фиксирует оба захода целиком, одним файлом, чтобы не искать по двум записям.

## Решение
- Разбить `src/api/api.py` на файлы по одному на путь/ресурс (пункт 1).
- `status` в теле ответа — оставить как есть, уже реализовано (пункт 7).
- Параметры GET — перейти на query-строку вместо JSON-тела (пункт 5).
- HTTP-код ответа — `error_response`/`status_response` в `src/api/api.py` должны возвращать код вместе с телом (Flask принимает `(тело, код)`), а не только тело (пункт 6).
- Отдельный e2e-тест и подробный докстринг на метод (пункты 2–3) и атомарность через `rollback`/`commit` (пункт 4) — уже закреплённая практика, эта запись только фиксирует её осознанность.

## Почему
- **Один файл на ресурс:** `api.py` на 15 методов уже занимает ~1000 строк, что затрудняет навигацию; группировка по ресурсу — компромисс между «15 отдельных файлов» (максимальная изоляция, но дублирование импортов/декораторов) и текущим «всё в одном файле».
- **Отдельный e2e-тест на метод:** падение теста сразу указывает на конкретный сломанный метод, а не требует разбираться в общем файле.
- **Подробный докстринг:** единственный источник правды о контракте метода — по нему клиентская часть понимает формат ответа, а агент в следующей сессии восстанавливает контекст без чтения кода.
- **Атомарность:** частичная ошибка (например, статья создалась, а теги — нет) никогда не должна оставлять базу в противоречивом состоянии.
- **GET-параметры в query-строке:** браузерный `fetch` запрещает тело у GET, а XHR/axios его молча выбрасывает — значит настоящий GET с JSON-телом клиент из браузера вызвать не сможет. Это не вопрос вкуса, а жёсткое ограничение браузерных API.
- **`status` нужен для подробного разбора ошибок:** один HTTP-код 400 не различает «отсутствует обязательное поле», «неверный тип поля» и «статья с таким id не найдена» — а `error_type`/`message` в теле дают точную причину.
- **HTTP-код — стандартная практика и удобен на фронте:** у кода уже есть готовая инфраструктура на клиенте (interceptors в axios/fetch, автоматическая обработка 4xx/5xx, видимость в devtools/логах прокси), которой не пользуется API, всегда отвечающий 200.

## Варианты
### По файловой структуре (пункт 1)
- **Один файл на `api_<метод>_<тип>`** (15 файлов): максимальная изоляция, но дублирование импортов/декораторов на каждый файл.
- **Один файл на путь/ресурс (выбран):** компромисс — например `article.py` держит оба метода `/article`, `article_like.py` — `/article/like`.
- **Всё в одном файле (как сейчас):** проще на старте, но уже упёрлось в ~1000 строк на 15 методов.

### По HTTP-коду и status (пункты 6–7)
- **Код и status одновременно (выбран):** код — для быстрой маршрутизации на фронте, `status` — для точной причины ошибки; ни один канал не теряет информацию. Минус — два источника правды, которые нужно держать в согласии.
- **Только status, код всегда 200:** проще на бэкенде, но ломает стандартные HTTP-клиентские паттерны на фронте.
- **Только HTTP-код, без status в теле:** минимальный ответ, но не хватает гранулярности и текста сообщения — теряется ровно то, ради чего был введён `Status`/`ErrorType`.

### По параметрам GET (пункт 5)
Альтернатив по существу нет — это ограничение самого браузерного `fetch`/XHR, а не выбор дизайна. Единственный практический вопрос — когда переводить существующие методы; решили: не сразу, отдельной задачей.

## Примеры
Было (сейчас, во всех 15 методах):
```python
# GET читает параметры из JSON-тела, как и POST
is_right_structure, error = check_structure(request.json, api_info.article_get)
...
return status_response(status)  # Flask всегда отдаёт 200, даже при ERROR
```

Станет (в новых методах, по пунктам 5–6):
```python
# GET читает параметры из query-строки
is_right_structure, error = check_structure(request.args, api_info.article_get)
...
return status_response(status), http_code_for(status)  # например (тело, 404) для "not found"
```

## Последствия
- При разбивке `api.py` по файлам (пункт 1) нужно решить, куда переезжают общие хелперы `error_response`, `status_response`, `check_not_unlogged`, `get_session`, `check_structure`, `fill_default`, `check_list_elements` — сейчас они в одном файле и нужны всем.
- `error_response`/`status_response` нужно дополнить параметром/таблицей HTTP-кода (`ErrorType` → код; случай «не найдено» тоже сейчас `ValueError`, но должен маппиться на 404, а не на общий 400 — нужен отдельный признак, не только `error_type`).
- Переход GET-методов на query-строку меняет то, как `check_structure`/`fill_default` читают данные (`request.args` вместо `request.json`) и как об этом договариваются с `api_info.py`/тестами (сейчас там `container: "body"` даже для GET-полей).
- Полный перевод существующих 15 методов по пунктам 1, 5, 6 — отдельная задача, не делать без явной просьбы.
