# 0003. Авторизация через access/refresh токены вместо username в запросе

## Правило для агента
Личность вызывающего для всех методов, которым она нужна, определяется access
token'ом из заголовка `Authorization: Bearer <access_token>`, а не полем
`username` в теле запроса — такого поля у этих методов больше нет. Метод либо:
- **обязательно авторизован** (`require_auth` в api.py) — отсутствие/невалидность/
  истечение токена это `ValueError "Missing or invalid token"`;
- **опционально авторизован** (`optional_auth`) — отсутствие заголовка означает
  анонимного вызывающего (внутри — `"unlogged_user"`), но **присутствующий и
  невалидный** токен — это ошибка, а не тихий откат к анонимному доступу;
- **публичный** (регистрация, `/login`, `/auth/refresh`) — токен не участвует.

Новый защищённый или персонализированный метод обязан использовать
`require_auth`/`optional_auth`, а не принимать `username` от клиента как факт.

## Контекст
Раньше **любой** метод принимал `username` прямо в теле запроса и полностью ему
доверял — сервер никак не проверял, что вызывающий действительно тот, кем
представился. При проверке всех API-методов это уже всплывало как дыра:
`/article/like`, `/article/dislike`, `/article/comment` (POST) и лайки/дизлайки
комментариев не имели даже базовой проверки на `"unlogged_user"`, то есть
анонимный вызов мог поставить лайк или оставить комментарий от имени этой общей
псевдо-учётки. Пользователь прямо попросил добавить полноценную авторизацию по
токенам с временем жизни — «как это стандартно реализовано на обычных сайтах» —
и перевести на неё сразу все существующие защищённые методы.

## Решение
Стандартная связка access + refresh токен:
- **Access token** — короткоживущий (`config.access_token_lifetime_ms`, 1 час),
  летает в каждом запросе в `Authorization: Bearer`.
- **Refresh token** — долгоживущий (`config.refresh_token_lifetime_ms`, 30 дней),
  используется только на `/auth/refresh`, чтобы получить новую пару без повторного
  ввода пароля; **ротируется** при каждом использовании (старый удаляется, выдаётся
  новый) — повторное предъявление уже использованного refresh token не сработает.

Оба токена — случайные опаковые строки (`secrets.token_hex(32)`), хранятся в
новых таблицах `access_tokens`/`refresh_tokens` (см. `db/scheme.py`) с составным
поиском по `token` (PK) и `username` (index, для отзыва всех сессий разом).
Никакой подписи/криптографии сверх генерации токена не потребовалось — это то же
самое fan-out-решение, что уже принято для лайков/подписок (см. `decisions/0002`).

Новые методы: `POST /login` (было `GET /login`, теперь выдаёт токены вместо
`is-correct`), `POST /auth/refresh`, `POST /auth/logout`. Из всех остальных
защищённых/персонализированных методов поле `username` убрано из схемы
(`api_info.py`) — личность приходит из токена.

## Почему
- **Access + refresh, а не один токен.** Короткий access token ограничивает окно
  ущерба при краже (нельзя отозвать раньше срока, поэтому срок короткий); refresh
  token живёт долго, но его можно отозвать (logout, смена пароля) и он ротируется
  при использовании — обнаружение повторного использования старого refresh token
  сигнализирует о компрометации.
- **Опаковые токены в БД, а не JWT.** См. подробное сравнение вариантов ниже — на
  этом масштабе (без внешней криптозависимости, с уже принятым fan-out-подходом)
  проще и не требует новой библиотеки/своей реализации подписи.
- **`GET /login` → `POST /login`.** Метод теперь создаёт токены (побочный эффект),
  что нарушает семантику GET (должен быть safe/idempotent).
- **`/users/data` GET/POST больше не принимают `username`.** Раньше можно было
  запросить приватные поля (email, sub_tags, blocked_tags) **любого** пользователя,
  просто зная его username — реальная утечка приватности, закрытая тем же
  изменением, что убрало доверие к клиентскому `username`.

## Варианты
### Вариант A (выбран) — оба токена опаковые, в БД
- Плюсы: не нужна ни одна новая зависимость и ни строчки криптографии; тот же
  паттерн, что уже используется для лайков/подписок; отзыв — простое `DELETE`.
- Минусы: один лишний `SELECT` на каждый авторизованный запрос — незаметно на
  фоне уже существующих 10+ запросов на один ответ (`get_article_preview` и т.п.).

### Вариант B — access token как JWT (без обращения к БД), refresh — опаковый
- Плюсы: проверка access token не требует запроса к БД.
- Минусы: нужна подпись (`hmac`+`hashlib`+`base64` вручную, либо зависимость
  `PyJWT`, что требует обоснования); украденный access token нельзя отозвать
  раньше истечения.
- Почему не выбран: не даёт значимого выигрыша при этой нагрузке и добавляет
  код/зависимость, которых сейчас можно избежать.

### Вариант C — оба токена JWT
- Не рассматривался всерьёз: без хранения refresh token в БД его нельзя отозвать
  при logout/компрометации, что убивает смысл разделения на два токена.

## Последствия
- **Клиентской части:** нужно реализовать вход через `POST /login`, сохранять
  `access_token`/`refresh_token`, слать `Authorization: Bearer <access_token>` на
  все методы, которые его требуют (см. докстринги в `api.py` — раздел
  «Принимает» каждого метода явно говорит, обязателен токен, опционален или не
  нужен), обрабатывать `ValueError "Missing or invalid token"` вызовом
  `POST /auth/refresh`, и вызывать `POST /auth/logout` при выходе.
- Поле `username` в теле запроса убрано у всех методов, где раньше означало
  «действующее лицо» (see `api_info.py`): `/article` POST, `/article/like`,
  `/article/dislike`, `/article/comment` POST, `/article/comment/like`,
  `/article/comment/dislike`, `/users/data` GET/POST, `/users/password`. У методов
  с опциональной персонализацией (`/article` GET, `/article/data`,
  `/article/comment/data`, `/pages`) поле `username` тоже убрано — персонализация
  теперь целиком по токену.
- `/users/data` GET больше не принимает произвольный username — всегда отдаёт
  профиль владельца токена (см. «Почему» — заодно закрывает утечку приватности).
- Смена пароля теперь отзывает **все** токены пользователя — другие
  устройства/вкладки требуют повторного входа.
- `tests/conftest.py::add_user` теперь сразу логинится и возвращает
  `(username, password, nickname, email, access_token, refresh_token)` —
  6-элементный кортеж вместо 4-элементного.

## Условия пересмотра
- Если нагрузка вырастет настолько, что лишний `SELECT` на каждый запрос станет
  заметен — тогда пересмотреть в пользу варианта B (JWT access token).
- Если понадобится «выйти со всех устройств одной кнопкой» отдельно от смены
  пароля — уже есть `auth.revoke_all_tokens`, нужно только завести отдельный
  API-метод.
