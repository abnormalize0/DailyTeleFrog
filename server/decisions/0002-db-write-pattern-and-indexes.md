# 0002. Схема БД — запись через отдельные строки вместо счётчиков, индексы, план кэша

## Правило для агента
- Для «реакций»/связей многие-ко-многим (лайки, дизлайки, подписки, блок-листы, теги) — отдельная строка на каждую связь с составным `primary_key` из обеих сторон (как `ArticleLike`, `TagSubscription` и т.д. сейчас), а не общий столбец-счётчик на родительской сущности. Счётчики (`likes`, `dislikes`, `rating`) вычисляются на лету через `COUNT(*)`/разность, отдельно не хранятся.
- Ядро сущностей (`User`, `Article`) обновляется обычным `UPDATE` — это осознанно и не противоречит первому пункту (см. «Почему»).
- Любая новая часто используемая для поиска/сортировки колонка получает `index=True`, если не покрыта уже существующим составным ключом (см. «Что осталось сделать» — сейчас в схеме есть непокрытые колонки).
- Кэш агрегатов (`likes_count`/`rating` без пересчёта на каждый запрос) — осознанно отложен, **не в ближайшее время**. Не начинать без отдельной задачи и явной просьбы.

## Контекст
При проверке всех API-методов возник вопрос: почему схема БД устроена так, что лайки/дизлайки/подписки — это отдельные таблицы-связки, а не счётчик-поле на статье/комментарии/пользователе. Автор проекта пока слабо разбирается в БД, поэтому решение проговорили и перепроверили вместе, прежде чем фиксировать.

Идея была сформулирована как «минимизировать UPDATE, чтобы не блокировать доступ». При проверке выяснилось, что формулировка неточна: проект использует MySQL 8 без переопределения движка (`deployment/code_mysql.dockerfile`), то есть таблицы на InnoDB — там построчная блокировка и MVCC, из-за чего обычный `SELECT` никогда не блокируется `UPDATE` и наоборот, независимо от того, используется `UPDATE` или `INSERT`/`DELETE`. Настоящая опасность — не `UPDATE` сам по себе, а **«горячая строка»**: много конкурентных транзакций, пишущих в одну и ту же строку (например, все лайки статьи как инкременты одного и того же `likes_count`). Fan-out-таблицы решают именно это — у каждого лайка своя строка `(article_id, username)`, конфликтующих записей почти нет.

## Решение
1. Оставить fan-out-таблицы для реакций/связей как есть — это уже написанная и оттестированная схема, менять не нужно.
2. Не заводить столбцы-счётчики сейчас.
3. Добавить недостающие индексы на колонки, которые сейчас не покрыты ни одним ключом, но участвуют в поиске/сортировке (список ниже).
4. Кэш агрегатов — зафиксировать как осознанно отложенный план, не делать сейчас.

## Почему
- **Fan-out вместо счётчика:** каждая связь — своя строка с составным PK из обеих сторон — даёт идемпотентность «из коробки» (один пользователь — один лайк на статью, гарантирует сама база) и не создаёт горячую строку при всплеске активности на одной статье. Это стандартный приём именно против конкурентной записи в общий агрегат.
- **`UPDATE` на `User`/`Article` — это нормально:** свою запись обновляет только сам пользователь (смена ника, пароля), конфликтов почти не бывает, MVCC InnoDB и так не блокирует читателей на время такого `UPDATE`.
- **Индексы нужны отдельно от «нет блокировок»:** отсутствие горячих строк не отменяет того, что `COUNT`/`WHERE`/`ORDER BY` по непокрытой ключом колонке — это full scan при росте таблицы. Это цена, которую выбранный подход перекладывает с записи на чтение (см. «Минусы» в вариантах ниже), и её нужно явно компенсировать индексами.
- **Кэш агрегатов отложен осознанно, а не забыт:** при нынешнем масштабе (портфолио-проект, до ~50 пользователей по своей же оценке) пересчёт `COUNT` на каждый запрос дешевле, чем поддерживать согласованность денормализованного кэша. Откладывается до реального роста нагрузки, а не выполняется «на всякий случай».

## Варианты
### Вариант A (выбран) — fan-out-таблица + `COUNT` на чтение
- Плюсы: идемпотентность через PK, нет горячих строк, источник правды один (сами события лайка/дизлайка) — можно пересчитать агрегат в любой момент.
- Минусы: цена агрегата перекладывается на каждое чтение; при росте таблицы и отсутствии индекса — full scan; сортировка ленты по рейтингу (`_rating_expression()` в `article.py::pages_get`) — коррелированный подзапрос на каждую строку выдачи, самое дорогое место при росте числа статей.

### Вариант B — счётчик-столбец с атомарным `UPDATE ... SET count = count + 1`
- Плюсы: O(1) чтение агрегата, не нужен отдельный кэш.
- Минусы: становится горячей строкой при всплеске активности на одной статье; нет встроенной идемпотентности — защиту от повторного лайка того же пользователя пришлось бы делать отдельной проверкой в коде, а не PK.

### Вариант C — денормализованный кэш агрегата поверх fan-out-таблиц (счётчик-столбец или Redis, обновляемый асинхронно/по событию)
- Плюсы: и дешёвая запись (fan-out, как сейчас), и дешёвое чтение агрегата.
- Минусы: два источника данных, которые могут разойтись; нужна инвалидация/пересчёт; лишняя сложность при нынешней нагрузке.
- Статус: не отклонён, а сознательно отложен — см. «Что осталось сделать».

## Условия пересмотра
- Индексы — сделать при первой же задаче, которая трогает соответствующую таблицу, не откладывать вместе с кэшем: это дешёвое исправление без изменения формы данных.
- Кэш агрегатов — вернуться к вопросу, когда: (а) реальная нагрузка сделает пересчёт `COUNT` заметно медленным (в частности сортировку ленты по рейтингу), или (б) появится конкретная жалоба на скорость `/pages`.
