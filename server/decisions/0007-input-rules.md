# 0007. Минимальные правила ввода для аккаунта и контента

## Правило для агента
Описывай ограничения поля в схеме `api_info.py`, а не в коде метода. Для данных аккаунта используй общие `_USERNAME_RULES`, `_NICKNAME_RULES`, `_EMAIL_RULES` и `_NEW_PASSWORD_RULES`. При входе эти правила не применяй.

## Контекст
Проверка всех методов некорректными запросами показала, что регистрация принимала пустые строки, NUL-символы и невалидный email, а API принимал статью с пустым заголовком и пустой комментарий. Пользователь попросил добавить минимальные проверки по принятым в индустрии нормам.

## Решение
| Поле | Правило |
|---|---|
| `username` | 3–32 символа, латинские буквы, цифры, `_` и `-` |
| `nickname` | до 32 символов, хотя бы один видимый символ, без управляющих символов |
| `email` | до 255 символов, вид `имя@домен.зона` |
| `password`, `new_password` | 8–128 символов, без требований к составу |
| `title` статьи, `text` комментария | хотя бы один видимый символ |
| теги в `tags`, `sub-tags` и `blocked-tags` | хотя бы один видимый символ |
| `body` статьи | не пустой объект |

Видимым не считается всё, что выглядит как пустота: пробелы любой ширины, табы, переносы строк, управляющие и форматирующие символы (например U+200B) и символы-заполнители (например U+3164). Символ определяется по категории Unicode из `unicodedata`, заполнители перечислены в `shared._INVISIBLE_CHARS`.

В схеме появились ключи `min_length`, `not_blank`, `item_not_blank`, `pattern` и `pattern_reason`. Клиент получает их через `OPTIONS`.

## Почему
Схема уже хранит пределы длины и отдаёт их клиенту, поэтому новые правила ложатся туда же и действуют на всех методах. Длина пароля и отказ от требований к составу следуют NIST SP 800-63B: обязательные классы символов приводят к предсказуемым паролям. Email проверяется грубо, потому что существование адреса подтверждает только письмо.

## Варианты

### Правила в схеме api_info (выбран)
- Плюсы: один источник правил для сервера и клиента, проверка работает автоматически в `check_endpoint_structure`.
- Минусы: `pattern` должен быть совместим с регулярными выражениями JavaScript.

### Проверки в коде методов
- Минусы: правила пришлось бы дублировать в `POST /users` и `PATCH /users/me`, а клиент бы их не видел.
- Почему не выбран: дублирование и риск обойти правило через другой метод.

## Последствия
- Клиенту нужно показывать новые причины отказа из `errors` и не отправлять пустые статьи и комментарии.
- Вход не проверяет формат: иначе аккаунты, созданные до появления правил, не смогли бы войти, а ответ раскрывал бы правила вместо единой ошибки.
- `preview` статьи на пустоту не проверяется.
- `include_tags` и `exclude_tags` в ленте не проверяются: это фильтры, они ничего не записывают.
- Символы, которых нет в базе Unicode этой версии Python, считаются видимыми: иначе новые эмодзи отвергались бы как пустота.

## Условия пересмотра
Когда появится подтверждение email или понадобятся кириллические username.
