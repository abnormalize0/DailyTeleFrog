# 0009. Атомарность API-методов

Уточняет пункт 4 из [0004](0004-rest-api.md): там записан паттерн, а здесь его смысл и способ проверки.

## Правило для агента
- API-метод атомарен: при ответе 2xx применены все его изменения, при любом другом ответе не изменилась ни одна строка ни одной таблицы.
- Один запрос выполняется в одной сессии с одним `commit`. `commit` и `rollback` вызываются только в `src/api/routes/`. `src/backend.py` и `src/db/` делают только `flush`.
- Метод с двумя и более записями получает тест в `tests/routes/test_atomicity.py`: сбой последней записи через `fail_write`, сравнение `read_all_rows()` до и после запроса.
- Запись, которая должна пережить ошибочный ответ, противоречит правилу. Такой случай сначала обсуди с пользователем.
- Проверка перед записью не защищает от параллельного запроса, поэтому конфликт ключа не должен давать 500. Строку-связь добавляй через `rows.add_if_missing`. Если значение обязано быть уникальным, перехватывай `IntegrityError` при `flush` и возвращай `Status` с ошибкой. `rollback` при этом остаётся за методом.
- Сервер работает на READ COMMITTED (`shared.get_session`). Если взаимоисключающие строки лежат в разных таблицах, ключ их не защитит: блокируй строку владельца перед чтением, как `rows.lock_user_reactions`. Блокирующее чтение несуществующей строки не используй.

## Контекст
Задача `issues/0004-api-atomicity.md`. Пункт 4 из 0004 описывал только паттерн и ничем не проверялся.

## Решение

### Что считается атомарностью
Речь об одном запросе: все изменения применяются вместе или не применяются совсем. Выход из `with get_session()` без `commit` откатывает транзакцию, поэтому ранний `return` и необработанное исключение тоже ничего не меняют. Явный `session.rollback()` в ветке ошибки сохраняется как обязательная часть шаблона: он показывает читателю, что произойдёт.

Параллельные запросы в это определение не входят: связку «проверили, потом записали» не защищают ни REPEATABLE READ, ни READ COMMITTED. Частичных записей такие запросы не оставляют, но конфликт ключа не должен доходить до клиента как 500.

### Конфликты параллельных запросов
- `rows.add_if_missing` вставляет строку-связь в точке сохранения. Повтор считается успехом, а остальные изменения запроса сохраняются. Через эту функцию идут реакции, подписки, блокировки и история имён.
- `user.add_user` и `user.update_email` перехватывают `IntegrityError` при `flush` и возвращают 409. Транзакция к этому моменту уже откачена, поэтому `add_user` не различает username и email и отвечает общим текстом `Username or email is already taken`.
- Лайк и дизлайк лежат в разных таблицах, поэтому ключ не запрещает им существовать вместе. `rows.lock_user_reactions` блокирует строку пользователя, и `PUT` реакций одного пользователя выполняются по очереди. Реакции разных пользователей друг друга не ждут.
- Сервер работает на READ COMMITTED. Иначе запрос, дождавшийся блокировки, читал бы снимок из начала транзакции и не видел бы реакцию предыдущего запроса.

### Результат проверки методов
Просмотрены все методы в `src/api/routes/`. Каждый работает в одной транзакции, правило соблюдается.

| Методы | Записей | Что проверяется в `test_atomicity.py` |
|---|---|---|
| `POST /articles` | статья, предпоказ, теги | сбой записи тегов и одинаковые теги |
| `PUT` лайка и дизлайка статьи и комментария | снятие прежней реакции, новая реакция | сбой вставки новой реакции |
| `POST /auth/login` | access, refresh | сбой записи refresh |
| `POST /auth/refresh` | отзыв старого, access, refresh | сбой записи refresh |
| `POST /auth/logout`, `POST /auth/logout-all` | access, refresh | сбой отзыва refresh |
| `PATCH /users/me` | любое число полей и связей | ошибка в последнем значении и сбой записи |
| `DELETE /users/me` | аккаунт, связи, токены | сбой отзыва refresh |
| `PUT /users/me/password` | пароль, токены | сбой отзыва refresh |
| `POST /users`, `POST /articles/{id}/comments`, `DELETE` статьи, комментария и реакций | одна | тест не нужен |
| Все `GET` | нет | тест не нужен |

### Как проверяется
- `tests/routes/test_atomicity.py`: сервер получает настоящую ошибку MySQL на последней записи, после чего тест сравнивает содержимое всех таблиц со снимком.
- `tests/routes/test_concurrency.py`: одновременные одинаковые запросы не дают 500. Unit-тесты воспроизводят ту же гонку детерминированно: `open_snapshot` фиксирует снимок транзакции, а `commit_rows` коммитит строку из другой транзакции. Проверка её не видит, а ключ видит.
- `src/api/tests/test_transactions.py`: разбор исходников без запуска. `commit` и `rollback` есть только в `routes`, у каждого метода не больше одной сессии и одного `commit`. Эта проверка работает и для новых методов, у которых ещё нет своего теста.
- `make test-env` запускает тестовую MySQL с `--log-bin-trust-function-creators=1`: иначе пользователю без SUPER нельзя создавать триггеры.

## Почему
- **Снимок всех таблиц** находит и то, что не видно по HTTP, например запись в `user_name_history`. Новая таблица попадает под проверку сама.
- **Триггер вместо мока:** сервер работает в отдельном процессе, а по решению [0010](0010-unit-tests.md) моков в проекте нет. Откат выполняет настоящая база, а сбой можно поставить на конкретную запись.
- **Параллельные запросы отдельно от определения:** атомарность обеспечивает транзакция, а конфликты между запросами решаются ключами БД, поэтому и проверяются они разными тестами.
- **Точка сохранения для повторов:** она не замедляет запросы к другим строкам и требует правки в одной функции.
- **READ COMMITTED для всего сервера:** уровень нельзя сменить посреди транзакции, а снимок открывается ещё при проверке токена. Цена небольшая: разные запросы внутри одного чтения могут увидеть данные на чуть разные моменты времени, например счётчики на странице статьи.

## Варианты

### Триггер на настоящей базе (выбран)
- Плюсы: без моков, точное место сбоя, код сервера не меняется.
- Минусы: нужен флаг у тестовой MySQL, тест зависит от того, какая запись идёт последней. Выбор проверен запуском с `AUTOCOMMIT` и `add_if_missing` без точки сохранения, которая в этом режиме не работает: падают все 14 тестов.

### Подмена функций в тестовом режиме сервера
- Минусы: в продакшн-коде появилась бы ветка только для тестов.
- Почему не выбран: триггер даёт то же без изменений в сервере.

### Только статическая проверка
- Плюсы: быстро, ничего не нужно настраивать.
- Минусы: не доказывает, что данные действительно не меняются.
- Почему не выбран: задача требует проверки данных. Статическая проверка осталась дополнением.

### Защита от лайка и дизлайка одновременно: блокировка и READ COMMITTED (выбран)
- Плюсы: одна блокировка на четыре функции и одна строка настройки, схема не меняется.
- Минусы: уровень изоляции меняется для всего сервера. Правило держится на коде, а не на ключе БД.

### То же при REPEATABLE READ
- Минусы: баг остаётся, тест падает при каждом прогоне.
- Почему не выбран: дождавшийся блокировки запрос читает старый снимок.

### Блокирующее чтение реакции при REPEATABLE READ
- Плюсы: уровень изоляции не меняется.
- Минусы: чтение несуществующей строки блокирует промежуток индекса, и разные пользователи на одной статье получают взаимоблокировки MySQL и 500. Это воспроизвелось в 4 прогонах из 4.
- Почему не выбран: чинит редкий случай ценой обычного.

### Одна таблица реакций с полем типа
- Плюсы: инвариант гарантирует первичный ключ, блокировка не нужна.
- Минусы: меняются схема, запросы и решение [0002](0002-db-write-pattern-and-indexes.md).
- Почему не выбран: для одного бага слишком большая правка. Вариант стоит вернуть, если появятся другие взаимоисключающие реакции.

## Последствия
- Для клиента меняется одно: при проигранной гонке регистрации он получает 409 с текстом `Username or email is already taken`. Параллельные запросы, которые раньше давали 500, теперь отвечают обычными кодами.
- Просроченные токены удаляются при успешных `login` и `refresh`. Токены пользователей, которые больше не вернутся, остаются в таблицах (см. `issues/0006-account-security.md`).
- Прогон e2e-тестов стал дольше примерно на две с половиной минуты.
- `POST /auth/refresh` с одним токеном при одновременных запросах успешно отвечает больше одного раза: во всех 15 раундах по 8 запросов. Это оставлено осознанно: последовательный повтор отклоняется, а строгая одноразовость выбросила бы из аккаунта вторую вкладку. Решается вместе с обнаружением кражи в `issues/0006-account-security.md`.
- Пропускная способность встроенного сервера Flask около 20 запросов в секунду на `GET /articles/{id}`. Дальше ответы замедляются до 1–3 секунд, ошибок при этом нет.

## Условия пересмотра
- Если появится запись, которая обязана пережить ошибочный ответ (например, счётчик неудачных входов для ограничения попыток из `issues/0006-account-security.md`), понадобится исключение из правила и отдельная транзакция.
- Если на продакшене `binlog_format` окажется не `ROW`, READ COMMITTED работать не будет. В MySQL 8 значение по умолчанию подходит.
- Если объекты начнут удаляться физически, `add_if_missing` придётся отличать повтор от нарушения внешнего ключа.
- Если появятся фоновые задачи или внешние сервисы, определение придётся расширить: транзакция БД на них не распространяется.
