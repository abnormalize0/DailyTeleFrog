# 0005. Мягкое удаление аккаунтов, статей и комментариев

## Правило для агента
1. Аккаунт, статья и комментарий не удаляются из таблицы: API ставит `is_deleted = True`.
2. Новый запрос к `users`, `articles` или `comments`, который отдаёт данные наружу, обязан учитывать `is_deleted`. Для проверки доступа используй `is_user_not_exist`, `is_article_not_exist` и `is_comment_not_exist`: удалённый объект для них не существует.
3. Удалённая статья и удалённый аккаунт не отдаются вообще. Удалённый комментарий отдаётся только заглушкой, без автора и текста.

## Контекст
При разборе схемы (задача `issues/0001`) понадобилось удаление статьи. Физическое удаление комментария разрывало бы ветки ответов, поэтому пользователь выбрал отметку об удалении: комментарий выводится заглушкой, как на Хабре.

## Решение
- Поле `is_deleted: bool` в `users`, `articles` и `comments`.
- Методы `DELETE /articles/{id}`, `DELETE /comments/{id}` и `DELETE /users/me`. Удалить можно только своё: статью и комментарий удаляет автор, аккаунт удаляет владелец с подтверждением паролем в теле запроса.
- **Статья.** Все методы отвечают 404, её нет в ленте. Вместе с ней скрыто всё внутри: комментарии, реакции, теги и предпоказ. Её реакции не входят в рейтинг автора.
- **Комментарий.** В дереве остаётся узел с `id`, `parent_id`, `is_deleted` и `answers`, `GET /comments/{id}` отдаёт только `{"is_deleted": true}`. Реакции и ответы запрещены. В `comments_count` и рейтинг автора он не входит.
- **Аккаунт.** Вход запрещён, токены отозваны, подписки и блокировки других пользователей на него сняты, новые оформить нельзя. Статьи и комментарии остаются, в `author_preview` отдаётся только `{"is_deleted": true}`. Комментарии сохраняют `author_username`.

## Почему
- Заглушка сохраняет ветку ответов: ответы других людей не должны пропадать вместе с чужим комментарием.
- На каждую сущность есть одна проверка существования, поэтому она закрывает все методы сразу, и новый метод получает правильное поведение автоматически.
- Статьи удалённого аккаунта остаются, потому что вместе с ними исчезли бы чужие комментарии и обсуждения. Пользователь подтвердил этот выбор.

## Варианты
### Вариант A (выбран): поле `is_deleted`
- Плюсы: ветки целы, данные можно вернуть, нет проблем с внешними ключами.
- Минусы: каждый запрос должен учитывать поле, данные остаются в базе.

### Вариант B: физическое удаление
- Плюсы: база не хранит лишнего, запросы проще.
- Минусы: ответы теряют родителя. Каскад по `parent_id` MySQL ограничивает 15 уровнями (ошибка 3008).
- Почему не выбран: ломает ветки комментариев.

## Последствия
- Username и email удалённого аккаунта заняты навсегда, а email и хеш пароля остаются в базе. Пользователь подтвердил это поведение.
- Реакции удалённого пользователя продолжают считаться.
- `parent_id` объявлен с `ondelete="SET NULL"`, чтобы строку статьи можно было удалить вручную при любой глубине веток.

## Условия пересмотра
- Если понадобится скрывать статьи вместе с аккаунтом или удалять персональные данные.
- Если появится восстановление удалённых объектов.
