# 0008. Неавторизованный пользователь обозначается значением None

## Правило для агента
В слоях `backend` и `db` проверяй анонимность через `username is None`. Не вводи служебных значений внутри пространства имён пользователей.

## Контекст
Анонимный вызывающий обозначался строкой `"unlogged_user"` (упомянута в решении 0003). Эта строка была обычным допустимым username: такой аккаунт регистрировался, но войти в него было нельзя, а личные фильтры ленты для него не сработали бы.

## Решение
`shared.optional_auth` возвращает `(None, None)`, если заголовка `Authorization` нет. `article.pages_get` проверяет `username is not None`. Функции, которые принимают анонимного вызывающего, объявляют `username: str | None`. `shared.check_not_unlogged` удалена, имя `unlogged_user` стало обычным.

## Почему
`None` нельзя получить из тела запроса как username, поэтому конфликт с именем пользователя невозможен в принципе, и отдельных запретов не нужно. Запросы `username == None` дают `IS NULL` и не находят строк, поэтому `is_liked` и `is_disliked` для анонима возвращают `False` без отдельной ветки.

## Варианты

### None (выбран)
- Плюсы: самое простое решение, тип `str | None` виден в сигнатурах.

### Отдельный класс или объект-маркер
- Минусы: нужен новый тип и преобразование перед каждым запросом к БД.
- Почему не выбран: сложнее без выигрыша.

### Запрет имени при регистрации
- Минусы: строка остаётся в логике, а запрет надо помнить в каждом методе.
- Почему не выбран: лечит симптом.

## Последствия
Клиент ничего не замечает: значение наружу не передаётся. Новый метод с `optional_auth` должен принимать `username` как `str | None`.
